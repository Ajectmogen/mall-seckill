## 下单链路改了什么

原来的写法是先查库存再扣（`select` 拿到值，`update` 写回去），并发下两个请求都能读到同一份余量，于是超卖。改成一条带条件的 UPDATE：

```sql
UPDATE pms_sku_stock
SET stock = stock - #{quantity}, lock_stock = lock_stock + #{quantity}
WHERE id = #{id} AND stock >= #{quantity}
```

影响行数为 0 就说明没扣动，直接返回失败。判断和扣减在同一条语句里，不需要额外加锁。

状态流转（支付回调、用户取消、超时取消）都改成带 `status` 条件的更新，`updated == 0` 当作"已经被别人处理过"直接返回。支付回调里同时校验金额，避免重复扣减和积分重入账。

延迟取消消息原来在手写事务里发，事务回滚了消息却已经投出去，消费者会去取消一个还不存在的订单。改成 `TransactionSynchronization.afterCommit` 之后再发，并保留 `OrderTimeOutCancelTask` 做兜底。

## 秒杀

一块是 Redis + Lua 预扣：库存和"已购会员"放在 Redis，`seckill.lua` 里先扣库存、再写买家集合，两个操作在一个脚本里，不会出现扣了库存没记买家的情况。数据库侧还有一道 `sms_flash_promotion_record` 的 `uk_relation_member` 唯一键，一个人一个场次只能一条。

v1 是同步建单：Lua 扣完名额就在当前线程里写订单，接口等数据库返回。压测时这部分 P99 是 924ms。

v2 改成 MQ 异步：Lua 扣完先落一条 `status=0` 的排队记录，事务提交后发消息，接口直接返回"排队中"，前端轮询 `/order/flash/result`。消费者用 `UPDATE ... SET status=10 WHERE status=0` 抢记录，抢不到就是重复消息，丢掉即可。建单失败、消息丢失、消费者异常三种情况分别用定时重投、超时判失败、死信队列兜住，恢复名额都是先还 Redis 再改状态。

售后有 `FlashPromotionReconcileTask` 每五分钟对一次账：Redis 剩余库存 + 买家数 和数据库口径比一下，不一致只打日志不自动修——扣减和落库之间有毫秒级窗口，自动修容易误伤正在下单的请求。

## 测出来的数

下单链路，每档 2000 个请求：

| 并发 | QPS | P50 | P99 |
|---|---|---|---|
| 20 | 432.2 | 44ms | 76ms |
| 50 | 416.2 | 113ms | 217ms |
| 100 | 380.5 | 239ms | 534ms |
| 150 | 340.4 | 365ms | 883ms |
| 300 | 281.8 | 552ms | 1320ms |

业务失败和系统错误都是 0。

150 并发的时候用 JFR 录了一段，`jdk.ThreadPark` 事件 1790 个，其中 1525 个（85%）停在取 Druid 连接上：832 次 `DataSourceTransactionManager.doBegin`、693 次 `SpringManagedTransaction.openConnection`，平均等 177ms。同一时间 MySQL 的 `Threads_connected` 一直是 21，而连接池 `max-active` 是 20，等于池子满了。

看着像连接池的问题，不像 Redis 的。粗算一下也对得上：20 个连接 × 每次 44ms ≈ 455 QPS，和 20 并发时测到的 432 接近。CPU 400%（20 核）、full gc 0 次、慢查询 0、Redis slowlog 空，都指向连接等待而不是计算或 IO 打满。

秒杀，2000 个不同会员抢 100 件：

- 成功 100、业务失败 1900、异常 0
- QPS 590、P50 136ms、P95 239ms、P99 845ms
- 之后核对了 `sms_flash_promotion_record` 的行数、会员有没有重复、`lock_stock` 有没有负数，都正常

同一个会员 50 并发只成功 1 单；1000 个会员抢 100 件也只成功 100 单。

v1 换 v2 之后，受理请求的 P99 从 924.69ms 降到 192.39ms。

我当时自己又用 JMeter 跑了一遍小规模（100 件库存，20/50/100/150 并发）：

| 20 | 20 | 0 | 64ms | 312 req/s |
| 50 | 50 | 0 | 181ms | 276 req/s |
| 100 | 100（售罄） | 0 | 206ms | 476 req/s |

## 两个数据一致性的坑

**超时取消把库存扣成负数**：`OrderTimeOutCancelTask` 释放库存时没判断订单当前状态，也没检查下限。订单已经被用户手动取消过一次，任务再跑一遍就再还一次，`lock_stock` 被减成 -24。修法是更新时带 `andStatusEqualTo(0)`，`updated == 0` 就 continue；释放语句再加 `AND lock_stock >= CASE ... END` 的下界。

**重复消费导致重复建单**：秒杀消息投递失败会重投，消费者必须自己对 `status` 做 CAS，否则一个会员会出两张单。唯一键只能兜住"同一会员同一场次"，兜不住"同一记录被消费两次"。

## 没做的事

- `mall-search` 的 ES 接入没验证，本机没有 9200
- 普通下单链路没上 Redis 预扣。单库场景下 DB 条件更新已经够，多一层 Redis 只会多一份"Redis 扣了但落库失败"的补偿工作。秒杀才需要把闸门前移
- 没有做分布式限流和热点商品隔离
