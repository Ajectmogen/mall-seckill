# mall-1 优化方案与实测报告（对比原版 mall）

> 基线：`D:\JavaProject\mall`（原版）→ `D:\JavaProject\mall-1`（优化版）
> 运行验证：2026-10-26（下单链路 36 项）+ 2026-10-27（压测 + 秒杀模块）
> 技术栈：Spring Boot 3.5.14 + JDK 17 + MySQL(mall1) + Redis(db1) + RabbitMQ(vhost `/mall`)，端口 8185

## 0. 一句话结论

> "mall-1 在原版 mall 基础上重做了**下单链路的并发安全**：把'先查库存再扣库存'的 check-then-act 改成**数据库层单条原子 UPDATE 预扣 + 影响行数校验**，把支付回调、用户取消、超时取消三条状态流转全部改成 **CAS 幂等**，并把延迟取消消息挪到**事务提交后**发送。我用真实启动的应用做了 36 项端到端验证：5 个会员并发抢 3 件库存恰好成交 3 单、8 线程并发支付同一订单只生效 1 次、重复执行超时任务不会重复释放库存、跨会员操作返回 403。
> 在此之上我又落地了**秒杀模块（Redis + Lua 预扣 + 一人一单 + 秒杀专用延迟队列 + 对账任务）**，并用真实压测验证：2000 个会员并发抢 100 件库存，成功数**恰好 100**、不超卖；同一个会员并发 50 次只成功 1 单。
> 需要说清楚的是：**普通下单链路我没有上 Redis 预扣**（单库、流量未到极限时，DB 原子 UPDATE 已经能保证不超卖，少一层'Redis 扣成功但落库失败'的一致性负担），**Redis + Lua 我放在了秒杀模块里**——秒杀是'瞬时流量极大、库存极少'的场景，闸门必须前移到 Redis。"

> ⚠️ 事实核对（2026-10-27 更新）：`mall-portal/src/main/resources/lua/seckill.lua` **已存在**并被 `FlashPromotionSeckillServiceImpl` 通过 `DefaultRedisScript` 调用；**普通下单链路仍然没有 Lua 也没有 Redis 预扣**——这是有意的设计取舍，不是"没做完"。旧版本文档里"全项目 0 个 .lua、秒杀只有建表 SQL"的说法已作废。

## 2. 已落地的优化点（相对原版 mall 改了什么）

### A. 下单链路并发安全（5 项，核心）

**A1. 库存预扣：check-then-act → 单条原子 UPDATE + 影响行数校验**
- 原版：`OmsPortalOrderServiceImpl` 先按 sku 查 `pms_sku_stock`，判断够不够，再 `updateByPrimaryKey` 逐条扣减 → 两步之间没有锁，并发下多个线程都判断"够"，造成超卖。
- 现在（`mall-portal/src/main/resources/dao/PortalOrderDao.xml:88-103` + `dao/PortalOrderDao.java:44` + `OmsPortalOrderServiceImpl.java:770-790`）：

```sql
UPDATE pms_sku_stock
SET lock_stock = lock_stock + CASE id WHEN #{skuId} THEN #{qty} ... END
WHERE id IN (...) AND stock - lock_stock >= CASE id WHEN #{skuId} THEN #{qty} ... END
```

```java
int rows = portalOrderDao.lockSkuStock(itemList);
//🩹 下界守卫未命中（扣减行数不足）说明库存数据异常：抛异常回滚
if (rows < itemList.size()) { Asserts.fail("库存不足，无法下单"); }
```
- **为什么能解决**：把"判断 + 扣减"合并成一条 SQL，由 InnoDB 行锁保证原子性；`stock - lock_stock >= qty` 是"可售库存"下界，天然不会超卖；影响行数不足即回滚事务。
- 实测：5 个会员并发抢 1 个 SKU 的 3 件库存 → 成功 3 单、失败 2 单（提示"库存不足，无法下单"），最终 `stock=3, lock_stock=3`。

**A2. 支付回调幂等：无条件更新 → CAS**
- 原版 `paySuccess` 直接 `updateByPrimaryKeySelective(order)`，重复回调（支付宝/微信重试）会重复扣库存、重复加积分。
- 现在（`OmsPortalOrderServiceImpl.java:269-292`）：

```java
OmsOrderExample example = new OmsOrderExample();
example.createCriteria().andIdEqualTo(orderId).andStatusEqualTo(0); // 仅待付款
int updated = orderMapper.updateByExampleSelective(order, example);
if (updated == 0) { return 0; }   // 🩹 已被处理过，直接返回，不再扣库存
```
- 实测：**8 个线程同时支付同一订单** → 只有 1 次返回 `1`，其余 7 次返回 `0`，库存只减 1。

**A3. 用户取消订单：无条件关闭 → CAS**（`OmsPortalOrderServiceImpl.java:330-345`）

**A4. 积分字段修复**：`order.setUseIntegration(orderParam.getUseIntegration())`（原版错用 `setIntegration`，且赋值位置在 insert 之后 → 落库为 NULL）；顺序调整为落库前（`OmsPortalOrderServiceImpl.java:190`、`:241`）。实测订单的 `use_integration=0` 已正常落库。

**A5. 延迟取消消息：事务内发送 → `afterCommit` 发送**（`OmsPortalOrderServiceImpl.java:250-258`）
- 原版在事务提交前 `sendDelayMessage`，消费者可能先于事务提交读到脏数据（订单还没落库）。
- 现在注册 `TransactionSynchronization#afterCommit` 再发。

### B. 本轮新增的 7 项加固

| # | 问题 | 改法 | 位置 |
|---|---|---|---|
| B1 | 超时取消定时任务用 `updateOrderStatus(ids,4)` 无条件更新 + 无下界释放锁定量 → 重复执行会把 `lock_stock` 扣成负数 | 改为**逐单 CAS**：`andStatusEqualTo(0)`，`updated==0` 直接 `continue`；释放锁定量随 CAS 成功才执行 | `OmsPortalOrderServiceImpl.java:294-325` |
| B2 | `@Transactional` 只写在接口上；实现类内部调用/回滚语义不可靠，`paySuccess` 的 CAS 与扣库存必须同事务 | 实现类补 `@Transactional(rollbackFor = Exception.class)` | `OmsPortalOrderServiceImpl.java:100 / 269 / 294 / 330` |
| B3 | 越权校验用 `order.getMemberId().equals(...)`，`member_id` 为空即 NPE → 500 | 先判空 + **把"当前会员 id"放在 equals 调用方**（会员一定非空） | `OmsPortalOrderController.java:56 / 60 / 101 / 116` |
| B4 | 购物车里同一 SKU 出现两行时，批量 `CASE id WHEN` 只命中第一个 `WHEN` → 影响行数不足被误判"库存不足" | 先按 skuId **合并数量**再扣减（`mergeSameSkuItems`） | `OmsPortalOrderServiceImpl.java:777-790 / 792-806` |
| B5 | `afterCommit` 里发 MQ 抛异常 → 接口返回 500，但订单已落库，消息永久丢失 | try/catch 只记 error 日志，交给超时定时任务兜底取消 | `OmsPortalOrderServiceImpl.java:250-258` |
| B6 | 购物车没有价格快照时（`/cart/add` 只传 productId+skuId+quantity），阶梯/满减/无优惠三个分支都**不回填 price** → `handleRealAmount` NPE（还被 Spring Security 的 `/error` 转发掩盖成 401） | 三个分支统一兜底：`price == null` 时回退 SKU 原价 | `OmsPromotionServiceImpl.java:73 / 101 / 177` |

### D. 秒杀模块 v1（Redis + Lua 预扣，2026-10-27 新增）

**D1. 三道闸门（设计主线）**

| # | 闸门 | 位置 | 作用 | 为什么不能只靠它 |
|---|---|---|---|---|
| 1 | **Redis + Lua 原子预扣** | `mall-portal/src/main/resources/lua/seckill.lua` | `GET stock` → 判重复 → `DECRBY` → `SADD buyers`，判断/扣减/记买家在 Redis 单线程内原子完成 | Redis key 可能丢失/过期，且不落库就没有凭据 |
| 2 | **成交记录唯一键** | `sms_flash_promotion_record` 的 `UNIQUE KEY uk_relation_member(relation_id, member_id)` | 一人一单的**最终兜底** | 只挡"同一会员重复"，挡不住"总量超发" |
| 3 | **复用普通下单的原子扣减** | `portalOrderDao.lockSkuStock`（见 A1） | 真正扣 `pms_sku_stock.lock_stock`，扣不动整单回滚 | 秒杀场景下 DB 不该是第一道闸门（会把连接池压垮，见 §4 压测） |

Lua 返回码：`>=0` 扣减后剩余库存、`-1` 未预热、`-2` 库存不足、`-3` 重复下单、`null` 脚本/Redis 异常（对外统一"秒杀服务暂不可用，请稍后重试"）。

**D2. 关键实现点**
- **价格服务端取**：从 `sms_flash_promotion_product_relation.flash_promotion_price` 读，不信任前端传来的金额（`FlashPromotionSeckillServiceImpl.java:298-419`）。
- **编程式事务**：用 `TransactionTemplate` 而不是 `@Transactional` —— 因为要按 `lockSkuStock` 的**影响行数**判失败，而方法内部 catch 之后声明式事务不会回滚，会写出"有订单、没锁库存"的半成品。
- **失败补偿**：Lua 扣减成功之后，落库任一步失败都要把 Redis 的库存加回去、把会员从 buyers 集合移除（`compensateRedis`；库存 key 已过期时不做 `incrby`，避免凭空造库存）。
- **秒杀专用延迟队列**：`mall1.flash.cancel` / `mall1.flash.cancel.ttl`，与普通订单的 `mall1.order.cancel` 隔离——秒杀的高并发取消消息不会把普通订单的取消堵在队头；发送同样在 `afterCommit`，失败只记日志，由超时任务兜底。
- **预热三条路径**：`POST /order/flash/preheat`（手工）、每分钟 `@Scheduled`（只预热"今天且时间段覆盖当前时刻"的场次）、下单遇到"未预热"时懒加载一次重试。
- **对账**：每 5 分钟比对「Redis 剩余库存/买家数」与「数据库口径」，只 `WARN` 不自动修复（Redis 扣减与落库之间有毫秒级窗口，自动修复会误伤正在下单的请求）。

**D3. 踩过的一个坑：预热把库存"还"回去了**
- 现象：预热原本是**无条件覆盖写** Redis 库存 key。如果它正好落在"Lua 已扣减、成交记录还没提交"的毫秒窗口里，就会把已经扣掉的库存还回去 → 让别的会员多抢（数据库唯一键只挡同一会员，挡不住不同会员）——**这是真实超发风险**。
- 修复：库存 key 改成 **SETNX**（只在 key 不存在时按数据库口径建立，抢购过程中绝不覆盖）；买家集合也只在"库存 key 新建或集合不存在"时重建。
- 定向验证（`probe_preheat.py`，自带 RESP 客户端直连 Redis，不依赖 redis-cli）：

| 步骤 | 操作 | 库存 key 的值 | 结论 |
|---|---|---|---|
| 1 | 清 key 后 `SET stock=100 EX 600`（造"抢购进行中"） | 100 | — |
| 2 | 调用预热接口（key 已存在） | **100（未变）** | 抢购中不覆盖 |
| 3 | `DECRBY stock 5`（模拟"已扣减、未落库"） | 95 | — |
| 4 | 再调用预热接口 | **95（未变）** | 修复前这里会被覆盖回数据库口径 → 会超发 |
| 5 | 清理三个 key | — | 环境交回给压测脚本 |

### E. 秒杀模块 v2（MQ 异步建单，2026-10-28 新增）

**E1. 为什么要异步**
v1 的用户等待路径里包含「锁库存 + 插订单 + 插明细」三次写库（实测成功请求 P99 ≈ 925 ms，见 §4.5）。v2 把建单挪到 MQ 消费者：下单接口只做「Lua 预扣 → 短事务 insert record(status=0) → afterCommit 发消息 → 返回 requestId」，同步部分只剩 Redis + 一次 insert。

**E2. 状态机（口径全项目统一）**

| status | 含义 | 谁写 | 占名额 |
|---|---|---|---|
| 0 | 排队中（Redis 已扣、消息已发、未建单） | 下单接口 | ✅ |
| 10 | 建单中（消费者 CAS 抢到） | 消费者 `UPDATE ... WHERE status=0` | ✅ |
| 1 | 待支付（订单已落库） | 消费者建单成功 | ✅ |
| 4 | 已支付 | 支付回调 | ✅ |
| 2 | 已取消（超时/主动取消） | 取消链路 | ❌ |
| 3 | 建单失败（名额已还，可重抢） | 消费者/死信/兜底扫描 | ❌ |

占名额口径 = `status IN (0,10,1,4)`（v1 是 `status <> 2`）：预热 `remain`、`reconcile()`、`verify` 脚本同步改成这个口径——这是 v2 最容易写错的地方。

**E3. 关键实现**
- **队列**：`mall1.flash.create`（direct，消息体仅 `Long recordId`）→ 消费抛异常进死信 `mall1.flash.dead`；延迟取消仍走 `mall1.flash.cancel.ttl`（独立于普通订单队列）。
- **消费幂等**：`UPDATE sms_flash_promotion_record SET status=10 WHERE id=? AND status=0`，`rows == 1` 才继续——重复投递直接被挡住。
- **建单**：`transactionTemplate` 内 `lockSkuStock`（影响行数 < 明细行数则 `Asserts.fail`）→ insert `oms_order`/`oms_order_item` → `updateOrderInfo` 置 `status=1`。
- **失败**：`compensateRedis` 归还名额 + `status=3` + `error_msg`；用户重抢复用同一行（撞 `uk_relation_member`，不能 insert 新行）。
- **兜底**：`FlashOrderCreateSweeperTask`（`@Scheduled(fixedDelay=10000)`）重投 `status=0` 超 15 s 的、把超 5 分钟未推进的判 3 并补偿。
- **开关**：`mall.flash.async-create`（`false` 回到 v1 同步路径，便于对比/回滚）。

**E4. 边界与注意**
- 构建注意：本会话沙箱对 `mall-portal/**` 无写权限，v2 是在 `.runcheck/build/proj` 镜像目录里 `mvn package` 出来的 jar（115,834,918 B）启动的；**真实终端里请就地重打包**（`mvn -o -pl mall-portal -am package -DskipTests -Ddocker.skip=true`）再 `bash .runcheck/restart_app.sh app7.log`，否则 `restart_app.sh` 会起旧 jar。
- 消息体是 Java 序列化的 `Long`（Spring 默认 `SimpleMessageConverter`），跨语言消费要换 JSON；死信只做兜底判定，无指数退避；「超 5 分钟判失败」只做了代码走查，未做故障注入。

## 3. 还没做的（如实记录，并给出设计）

### C1. 普通下单链路为什么不用 Redis + Lua（设计取舍，不是没做）
- 现状：**普通订单**防超卖靠 MySQL 原子 UPDATE（A1），普通链路里**没有** Redis 预扣；**秒杀链路已经落地 Redis + Lua**（见 2.D）。
- 讲法（先说取舍，再说如果要做怎么做）：
  - "普通下单我没有上 Lua，是因为在**单库、流量未到极限**的场景下，`UPDATE ... WHERE stock-lock >= n` + 影响行数校验已经能做到强一致且不超卖，少了一层'Redis 扣减成功但落库失败'的一致性负担；而且正常下单的库存竞争并不激烈，没必要把一致性风险前移。"
  - "什么时候该上？**秒杀**这种瞬时流量远大于库存量的场景——这也是我真正落地 Lua 的地方：①库存预热进 Redis；②Lua 里'判重 + 判库存 + 扣减 + 记买家'一次原子完成；③扣减成功后落库，失败就补偿（`incrby` 还回去 + 移出买家集合）；④每 5 分钟对账，只告警不自动修复；⑤还要防脚本刷单（一人一单 = Redis 集合前置拦截 + 数据库唯一键兜底）。"
  - 缺点也要讲：Redis 与 DB 双写一致性、Redis 宕机后的兜底（我的做法是 key 丢失时按数据库口径重建）、Lua 里不宜做复杂逻辑。

### C2. 缓存一致性 —— 未大规模落地（当前也没有脏读风险）
- 事实：全项目 **没有任何 `@Cacheable/@CacheEvict/@CachePut`**；`@EnableCaching` 在 `mall-security/src/main/java/com/macro/mall/security/config/RedisConfig.java:11`，`RedisCacheManager` 在 `mall-common/.../config/BaseRedisConfig.java:51-56`（TTL 1 天）**但没有任何业务方法使用**。
- 唯一真正在用缓存的：`mall-portal/.../service/impl/UmsMemberCacheServiceImpl.java`（`getMember/setMember/delMember` + `getAuthCode/setAuthCode`，key = `mall:ums:member:<username>`），`UmsMemberServiceImpl.java:148-154` 改完积分后 `delMember` → 属于最朴素的 **Cache Aside 删缓存**。
- 商品/订单不缓存，所以"改库后接口读到旧值"的现象不存在（实测：直接改 DB，`/product/detail` 立即返回新值）。
- 建议方案：
  1. **先更新 DB，再删缓存**（不是更新缓存），删失败用 MQ 重试（延迟双删）；
  2. 更强的做法：订阅 **binlog（Canal）** 异步删缓存，彻底解耦业务代码；
  3. **缓存穿透**：空值缓存 + 布隆过滤器；**击穿**：互斥锁/逻辑过期；**雪崩**：过期时间加随机值 + 多级缓存；
  4. 热点 key：本地 Caffeine + Redis 二级缓存。

### C3. 其他未做
- 限流/熔断（Sentinel）、链路追踪、监控告警（Prometheus/Grafana）都还没有。
- 秒杀模块的已知取舍：取消订单后只把 `record.status` 置 2，Redis 层放行但数据库唯一键仍然会挡（同一会员同一场次再下单会得到"您已参与过本次秒杀"）；秒杀单不叠加优惠券/积分。
- 压测只覆盖了下单/秒杀接口，没有覆盖加购物车、支付回调的完整链路。

### 4.4 真实压测：秒杀模块（`.runcheck/seckill/`）

夹具：`relationId=52`（`flash_promotion_id=15`、`session_id=8`、`sku_id=112`、**库存 100 件**、秒杀价 9.9、每人限购 1），真实会员账号 + 真实 token，先调预热接口建立 Redis 状态。

**第二轮（修复后，run_id `20261027-091508`，200 线程；每阶段前幂等重置夹具并预热）**：

| 场景 | 请求数 | **成功** | 重复下单 | 业务失败 | 异常/非 200 | QPS | P50 | P95 | P99 |
|---|---|---|---|---|---|---|---|---|---|
| P1：2000 个不同会员并发抢 100 件 | 2000 | **100（恰好等于库存）** | 0 | 1900 | 0 | 590 | 136 ms | 239 ms | 845 ms |
| P2：同一会员并发 50 次 | 50 | **1** | 49 | 0 | 0 | 255 | 69 ms | 102 ms | 104 ms |
| P2b：已抢到的会员再打 3 次 | 3 | 0 | 3 | 0 | 0 | — | 6 ms | 28 ms | 28 ms |
| P3：1000 个不同会员并发抢 100 件 | 1000 | **100** | 0 | 900 | 0 | 566 | 79 ms | 498 ms | 874 ms |
| **P4：抢购途中强制预热** | 2000 | **100** | 0 | 1900 | 0 | 752 | 72 ms | 149 ms | 1068 ms |

- **P4 是专门为「预热会不会把库存还回去」加的场景**：波次进行中插 3 次 `POST /order/flash/preheat`（2 次落在抢购窗口内，均 200），**没有任何一次把 Redis 库存变大**；再加一条**确定性探针**（先手工 `DECRBY` 5 件模拟「Lua 已扣、台账未落库」，此时无并发，再调预热）：库存 **95 → 95（Δ0）** —— 旧实现（无条件 `SET`）这里会按台账口径写成 0，等于把已扣的货还回去，所以这条能直接分辨新旧实现。
- **交叉校验**：`seckill_verify.py` **45 项检查全部通过、0 失败** —— 成交记录 301 = 成功订单 301、`count(distinct member_id)` 无重复、`pms_sku_stock.lock_stock` 逐阶段增量 = 成功件数、Redis 剩余库存 = 库存 − 成功数、订单号无重复、`/order/flash/reconcile` 自报与实测一致。
- **干扰项核查**：5 个阶段窗口内每分钟的定时预热执行 **0 次**（最近两次分别在窗口前/后 16 s），窗口内 ERROR 行 0 —— 所以「成功数 == 库存」不是被定时预热兜出来的。
- ⚠️ **两轮的 QPS/延迟差不能算作修复效果**：这次修复只改预热写 key 的语义（`SET` → `SETNX`），不在下单热路径；第一轮是应用刚重启后的首压（261 QPS / P50 433 ms），第二轮同档 590 QPS / P50 136 ms，属 JIT 与连接池 warmup。**正确性结论可跨轮对比，性能数字只做同一轮内横向对比**（要证伪得 A/B 交替多轮，本次没做）。
- 读法说明：P1/P3/P4 的「业务失败」是**预期**（库存抢完后其余请求收到「库存不足，秒杀失败」），HTTP 全 200、异常 0；成功请求要真正走完「Lua 扣减 → 落库 → 锁库存 → 发延迟消息」，延迟明显高于被 Redis 直接拒绝的请求 —— 这正是「闸门前移到 Redis」的价值：把 95% 的无效流量挡在数据库之外。

## 5. 剩余风险 / 下一步

1. `/cart/add` 直接信任客户端传来的 `price/productName` 等快照字段，下单用的又是购物车快照价 → **建议服务端按 skuId 回填真实价格**（否则可篡改价格）。秒杀链路已经做到了服务端取价。
2. `detail()` 在订单不存在时返回的是非 null 空壳对象（`OmsPortalOrderServiceImpl.java:432-438`：`new OmsOrderDetail()` + `copyProperties(null)`），现在靠 equals 顺序兜住 → 建议显式判空返回"订单不存在"。
3. `oms_cart_item` 缺 `(member_id, product_sku_id)` 唯一键 → 建议加唯一索引，从根上消除重复行。
4. 队列改名后，旧队列 `mall.order.cancel/.ttl` 里的历史消息不会被消费 → 建议清空或临时兼容消费。
5. `mall-search` 依赖 Elasticsearch：本机已装 8.18.8 + IK 分词器跑通（导入 20 个商品文档、关键词"手机"命中 5 条，见 `docs/ES本地部署与验证.md`），但还缺开箱即用的部署脚本与索引初始化流程。
6. 限流/熔断/监控（Sentinel、Prometheus/Grafana）尚未做；**压测数据已经有了**（见 4.3 / 4.4）。
7. 秒杀已升级 v2（MQ 异步建单，见 §2.E / §4.5）。剩余取舍：取消/失败后重抢复用同一行（唯一键挡新插入，不能 insert）；秒杀商品只支持单 SKU（`product_sku_id` 指定）；消息体是 Java 序列化 `Long`（跨语言要换 JSON）；死信无指数退避。
